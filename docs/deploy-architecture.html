自建 DevOps 平台 · 单 Docker Host 多独立 Compose · GitLab / Plane / Jenkins / Nexus / RagFlow + Nginx 统一入口 — 兼顾简单性、隔离性、可维护性、可备份性与可恢复性

01

总体部署架构

单台 Linux Docker Host / VM 承载全部核心应用。宿主机 Nginx 作为唯一对外 TLS 入口，反代到 Docker 内部网络 devops-internal。每个核心应用独立 Compose、独立生命周期，内部依赖（PG/Redis/ES/MinIO）由各自 Compose 自管并隔离在 default network。构建 Agent 可脱离 Docker Host 独立部署。

图 ① 总体部署架构：宿主机 Nginx → devops-internal → 各独立 Compose 应用 → 构建基础设施

推荐结论

每核心应用独立 Compose（gitlab / plane / jenkins / nexus / ragflow 各一份），内部依赖自管；external network devops-internal 只承载各应用的"对外服务容器"用于跨服务通信；宿主机 Nginx 作唯一 TLS 入口；对外只暴露 80/443（+ GitLab SSH）。构建 Agent 脱离 Docker Host 独立部署。

02

Compose 划分决策：一个还是多个

这是整套架构的根决策。从运维、升级、备份、故障隔离、迁移、扩容六个维度比较三种方案，结论明确指向"按数据边界拆分独立 Compose"。

维度方案 A：单 Compose 全量方案 B：每应用独立 Compose（依赖外部共享）方案 C：每应用独立 Compose（依赖自管）
运维复杂度低（一份文件）中中
升级复杂度高：任一服务 pull/up 全部重启低：单应用独立升级低：单应用独立升级
数据备份边界模糊，需手动拆分边界清晰边界最清晰：一应用一目录
故障隔离差：一服务崩易拖垮整体编排好好
网络隔离差：默认全互通中：依赖共享网络好：内部依赖锁在 default
依赖管理共享一份 PG/Redis（耦合）依赖外部共享组件自管，版本与应用匹配
版本管理所有依赖版本被迫统一共享组件升级影响多应用各应用各依赖版本独立
Compose 生命周期整体起停独立起停独立起停
宿主机迁移单文件好搬，但数据混在一起需迁应用+共享依赖按应用目录整体搬迁
灾难恢复整体恢复，粒度粗中好：按应用逐个恢复验证
后续扩容难拆分易易
推荐✗ 不推荐△ 可选✓ 强烈推荐

方案 A 为什么被否：中小团队看起来"一份文件省事"，但 docker compose up -d 是项目级操作——升级 RagFlow 会让 GitLab/Jenkins 跟着重启；PG/Redis 版本被 GitLab 和 Plane 绑死，谁也升不动；备份时所有 volume 混在一个项目里，灾难恢复只能"全有或全无"。

方案 B vs C 的关键区别在"内部依赖归谁管"：方案 B 抽一个共享的 PostgreSQL/Redis/MinIO Compose 给所有应用用，省内存但引入强耦合（Plane 升 PG 影响 RagFlow）。方案 C 让每个应用自带匹配版本的依赖，隔离在各自 default network。当前规模（单机、中小团队）选 C：内存多花一点（5 个 PG 实例），换来升级零耦合、迁移零牵连、故障零传染。等任一应用数据量增长到需要独立优化时，再单独抽基础设施也不迟。

图 ② Compose 划分：5 份独立 compose，各管各的依赖，共享一个 external network

03

Docker Network 深度分析

三种网络方案的取舍，以及为什么"external 共享网络 + 各自 default 网络"的双网络模型是当前规模的最佳解。

维度方案1：每 Compose 独立 network方案2：external 共享 + 各自 default方案3：完全共享一个 network
跨服务通信需 hosts/端口映射，DNS 不可跨 Compose容器名直连，DNS 全局可用直连
隔离性最强好：内部依赖锁在 default最差：全互通
攻击面最小可控（只对外容器上网）最大：PG/Redis 也暴露给邻居
服务发现困难alias 即服务名全局
升级影响网络重建可能断连external 不随 compose 重建无影响
配置复杂度高（需手动配互通）中（声明两个 network）低
推荐✗✓ 强烈推荐✗

方案 2 的核心思想：分层网络。每个应用有两个网络身份——default（项目私有，承载主服务 + 它的 PG/Redis/ES/MinIO，邻居进不来）和 devops-internal（external，只把"需要被别的应用访问的那个容器"挂上去）。这样 Nexus 能通过 http://gitlab 拉 GitLab，但 Nexus 碰不到 GitLab 的 PostgreSQL——后者只存在于 gitlab_default。

为什么不是方案 3：把所有容器（含 5 个 PostgreSQL、5 个 Redis、ES）全塞进 devops-internal，等于让 Jenkins 能直连 RagFlow 的 PostgreSQL、让 GitLab 能直连 Plane 的 Redis。隔离归零，攻击面拉满，某个容器被入侵后横向移动毫无阻力。违背"服务之间合理隔离"的硬性目标。

图 ③ Docker Network 架构：external 共享层 + 5 个隔离的 default 网络

04

服务发现：容器名 / 服务名 / alias

Docker 内置 DNS 在每个 user-defined network 上自动生效。关键是选对"被访问时用什么名字"，以及在哪里设。

方式说明跨 Compose?推荐
Container Name容器名（container_name:）全局唯一可可用但易撞名
Service Namecompose 内 service 名仅同 network 内同应用内部用
Network Alias在指定 network 上加别名可（在 devops-internal 上设）跨服务用 ✓
固定 IP手动指定—✗ 坚决不用
推荐

应用内部（如 gitlab 访问自己的 pg）用 service name：postgres。跨应用用 devops-internal 上的 network alias：gitlab / plane / jenkins / nexus / ragflow。统一小写短名，Nginx 和应用配置里都写 http://gitlab 这种。绝不依赖容器 IP。

给每个对外服务在 devops-internal 上显式设 alias，避免依赖 service name 的跨 Compose 解析行为差异：

services:
  gitlab:
    networks:
      default: {}          # 内部依赖走 default
      devops-internal:
        aliases:
          - gitlab         # 跨 Compose 用这个名访问

networks:
  default: {}
  devops-internal:
    external: true

这样 http://gitlab（来自 Nexus/Jenkins/Plane）、http://postgres（仅 GitLab 自己）都稳定可解析。Nginx 反代 upstream 也写 http://gitlab:80。

05

Nginx 放置：宿主机 vs 容器

Nginx 是平台入口，与单个应用生命周期解耦。比较两种放置方式后给出推荐。

维度宿主机 Nginx容器内 Nginx（独立 compose）
升级 Nginxapt 升级，不影响任何应用独立 compose up，需重启入口
证书续期certbot --restart nginx 最简单需 reload 容器
反代到容器127.0.0.1:port 或容器名(需入网)容器名直连(同 network)
宿主机端口占用80/443 占用80/443 映射
故障域Nginx 挂不影响应用容器同
统一性"宿主机也跑东西"破坏纯容器全容器化
推荐

宿主机 Nginx（当前规模首选）。理由：证书续期 + 升级链路最短、与 Docker 编排完全解耦、灾难恢复时 Nginx 装好即可恢复入口。若团队强烈要求"全容器化"，退一步用独立 nginx/compose.yaml 加入 devops-internal 并映射 80/443，也是可接受方案——但别把 Nginx 塞进某个应用的 compose。

HTTPS 证书：宿主机 certbot --nginx 自动签发 + 续期，证书放 /etc/letsencrypt，cron 自动 renew。WebSocket：所有 location 块加 proxy_http_version 1.1; proxy_set_header Upgrade $http_upgrade; proxy_set_header Connection "upgrade";（GitLab/Jenkins/Plane/RagFlow 都用 WS）。GitLab SSH：不走 Nginx，见下节。Docker Registry：走 Nexus 子域名 + client_max_body_size 0。

06

GitLab 特殊网络需求

GitLab 同时承载 HTTP/Webhook/Registry/SSH Git/API，是唯一需要"非 80/443 端口对外"的服务。

GitLab 流量走 Nginx?端口说明
Web UI / MR / API是443→gitlab:80标准反代
Container Registry是443→gitlab:5000子域名 reg.git.example.com 或 Nexus 托管
Webhook（入站）是443外网回调经 Nginx
Runner（出站拉取）内部—Runner 通过 devops-internal 访问 gitlab
SSH Git否22 / 2222必须直连 GitLab sshd

SSH Git 端口方案

方案 ①：宿主机 22 → GitLab（推荐专用机）

  • 宿主机 SSH 改到 2222 或禁用
  • git clone git@git.example.com:group/proj.git 标准体验
  • 适合 DevOps 专用服务器

方案 ②：宿主机 2222 → GitLab 22（推荐通用）

  • 宿主机保留 22 自用
  • ~/.ssh/config 设 Host git.example.com / Port 2222
  • clone: ssh://git@git.example.com:2222/group/proj.git
  • 互不干扰，最稳
推荐

方案 ②（宿主机 2222 → GitLab 22）。通用、零冲突、运维人员 SSH 不受影响。在 compose 里 "2222:22" 绑定宿主机。SSH Git 不走 Nginx（Nginx 是 HTTP 反代，无法代理 SSH 协议）。

Jenkins 与多架构 Build Agent

Controller 在 Docker，Agent 跨主机、跨 OS。关键是 Agent 通信协议选型与 Windows Agent 设计。

Agent 模式通信方向穿透性Windows 适配推荐
SSH AgentController→Agent:22需 Agent 开放端口需装 SSH 服务Linux 可用
Inbound Agent (JNLP/TCP)Agent→ControllerAgent 主动连，但需指定端口好可行
WebSocket AgentAgent→Controller:443(WS)走 443，穿透最佳好，不需 Docker✓ 强烈推荐
推荐

Controller 在 Docker（加入 devops-internal）；Linux Docker Agent 用独立容器 + WebSocket inbound；Windows Agent 用独立 Windows Server + WebSocket inbound agent（jar），不依赖 Docker。WebSocket 走 443，Windows Server 即使在不同网络/防火墙后也能主动连回 Controller，无需开放入站端口。

08

Nexus 网络：依赖 + 制品双角色

Nexus 同时是依赖代理（Maven/npm/NuGet，供 Build Agent 拉）和制品仓库（Docker Registry，供 CI 推/部署拉）。

  • Web UI：nexus.example.com → http://nexus:8081（Nginx 反代）
  • Docker Registry：reg.example.com → nexus:8082（独立子域名，client_max_body_size 0，支持 docker push）
  • Maven/npm/NuGet：开发者与 Build Agent 直接走 https://nexus.example.com/repository/...，由 Nexus 内部路由区分格式
  • 内部访问：Jenkins/Build Agent 通过 devops-internal 用 http://nexus:8081 直连，不经 Nginx，省一层 TLS
推荐

Nexus 单容器部署，blob store 挂宿主机卷。对外暴露 两个子域名：Web/UI/依赖走 nexus.example.com，Docker Registry 走 reg.example.com（必须独立域名，Docker client 按域名匹配 registry）。内部 CI 流量走容器名直连。

09

RagFlow：独立 Compose + 自管依赖

RagFlow 依赖 ES/OpenSearch、PostgreSQL、Redis、MinIO、可选 Embedding/LLM。选 B（与依赖同 Compose）。

选 A（依赖外部共享）会让 RagFlow 的 ES 版本与其他应用耦合，升级 ES 牵连一片。选 B 让 RagFlow 把它的全套依赖（官方 compose 已配好）原样带在身边，docker compose pull && up -d 整体升级，零外部牵连。

ragflow/
├── compose.yaml      # ragflow + es + postgres + redis + minio
├── .env              # LLM API Key / embedding 配置
└── data/             # 全部卷 bind 到这里，便于备份迁移

必须持久化的数据：PostgreSQL（知识库元数据/用户）、MinIO（原文档/解析产物）、Elasticsearch（向量+全文索引，最重）、Redis（可重建，缓存）、RagFlow 自身配置。LLM API Key 走 .env，不入库。

备份策略

策略频率内容保留
Daily每日 02:00全部 Critical 数据 + .env(加密) + compose + nginx 配置7 份
Weekly每周日 03:00同 Daily（全量）4 份
Monthly每月 1 号 04:00同 Daily（全量）6 份

必须备份（Critical）

  • GitLab 全量（含 secrets）
  • Nexus blob store
  • Plane PG + MinIO
  • RagFlow PG + MinIO + ES
  • Jenkins JENKINS_HOME
  • 所有 .env（加密）
  • Nginx 配置 + 证书

可重建（Rebuildable）

  • Jenkins pipeline 定义（在 GitLab）
  • Docker 镜像（重新构建）
  • 构建缓存
  • Redis 缓存数据
  • ES 部分索引（可重建，但耗时长，仍建议备份）
关键原则

热备优先于冷拷。PG 用 pg_dump，ES 用 snapshot API，GitLab 用 gitlab-backup create，Nexus 用停写 + blob tar——直接 tar 活动的数据库文件有损坏风险。每个应用单独备份脚本，输出到 /opt/devops/backup/<app>/，再统一压缩加密推异地。定期演练恢复（每月一次），没验证过的备份等于没有。

每个应用一个目录，内含 compose + .env + data + backup。这是备份/迁移的最小单元——整个目录 tar 走，到新机器解压即恢复。

评价

13

环境变量与 Secret

中小规模不需要 Vault。用 .env 文件 + 文件权限 600 + 备份时 GPG 加密，足够安全且零运维负担。

  • 每个 compose 目录一个 .env：DB 密码、初始管理员密码、SMTP、LLM API Key、对象存储密钥
  • 权限 chmod 600 .env，属主 root，不进 git（写 .gitignore），只保留 .env.example 模板进版本控制
  • 备份时 GPG 加密：tar ... | gpg -c > backup.tar.gpg，密钥单独保管
  • 不入 Vault 的理由：单机、单团队、内网为主——Vault 自身高可用部署比 5 个 .env 还复杂。等有多集群/多团队/动态密钥轮转需求再引入
# .env.example（进 git）
POSTGRES_PASSWORD=__CHANGE_ME__
GITLAB_ROOT_PASSWORD=__CHANGE_ME__
LLM_API_KEY=__CHANGE_ME__
SMTP_PASSWORD=__CHANGE_ME__
NEXUS_ADMIN_PASSWORD=__CHANGE_ME__

升级策略：单应用零牵连

"单应用单 Compose"的核心收益在此兑现。升级 RagFlow 不会重启 GitLab。

应用升级步骤影响范围
GitLab先 gitlab-backup create → 改镜像 tag → compose up -d → 跑内置 migrate仅 GitLab
Planecompose pull && up -d，内置 migrate仅 Plane
Jenkins改镜像 tag → up -d（插件在 UI 内升级）仅 Jenkins（Agent 不受影响）
Nexuscompose pull && up -d仅 Nexus
RagFlowcompose pull && up -d（含依赖一起升）仅 RagFlow
Nginxapt upgrade nginx / nginx -s reload短暂入口重载
注意：升级前必须备份该应用。GitLab 跨大版本（如 15→16）需按官方次序逐 minor 版本升级，不能跳级。数据库类依赖（PG）大版本升级要单独 pg_dump + 新版本 init + restore。

灾难恢复流程

假设宿主机整台损坏，凭异地备份在新 Linux 服务器恢复全套服务。8 步流程，目标是「装环境 → 建网络 → 恢数据 → 起服务 → 通入口 → 验证」。

docker network create devops-internal 3拉取 compose 仓库（git clone）+ GPG 解密恢复所有 .env 到各目录 4从异地备份 rsync 各应用 backup 快照到 /opt/devops/<app>/data/ 5按依赖顺序启动 compose：nexus → gitlab → plane → ragflow → jenkins 6恢复 Nginx 配置 + 证书 → nginx -t && systemctl reload nginx 7DNS 切换到新 IP · 逐个域名验证（curl/登录/clone/build 冒烟） 8恢复 Jenkins Agent：Linux Agent 重连 / Windows Agent 重启 agent.jar 全流程可脚本化（dr/restore-from-scratch.sh），目标 RTO ≤ 2h

16

最终推荐架构

综合以上分析，对当前规模（单 Docker Host、中小研发团队、自建）的明确推荐。不留选择题，全部给出定论。

决策项推荐方案理由
① 一个还是多个 Compose多个——每核心应用独立 Compose，内部依赖自管升级/备份/迁移/故障隔离全最优
② 是否用 external Network是，devops-internal跨 Compose DNS，不随 compose 重建
③ 哪些服务共享 Network5 个应用的"对外服务容器"（gitlab/plane/jenkins/nexus/ragflow）只需跨服务通信的容器上网
④ 哪些独立 Network每个应用自己的 default（含 PG/Redis/ES/MinIO）内部依赖锁死，邻居不可见
⑤ Nginx 放哪宿主机运行证书/升级链路最短，与编排解耦
⑥ 暴露哪些端口80/443（Nginx）+ 2222（GitLab SSH）唯一对外面，其余全内部
⑦ 哪些完全内部访问所有 Web UI、全部 PG/Redis/ES/MinIO、Docker Registry经 Nginx 或 devops-internal
⑧ 哪些必须持久化见 §10 表，全部有状态服务 bind mount 到 data/便于 tar 备份迁移
⑨ 哪些必须备份GitLab/Nexus/Plane/RagFlow/Jenkins Home + .env + Nginx 配置Critical 级，分级保留
⑩ 哪些可独立升级全部——每个应用互不影响单应用单 Compose 的直接收益

一句话总结

5 份独立 Compose + 1 个 external 网络 devops-internal + 各自 default 隔离内部依赖 + 宿主机 Nginx 统一 TLS 入口 + 仅暴露 80/443/2222 + bind mount 持久化 + 应用级热备 + .env(GPG) 管密钥。不引入 K8s/Swarm/Vault/Consul/Service Mesh——当前规模用不上，引入只会增加运维负担。等出现"多机横向扩展 / 多团队隔离 / 动态密钥轮转"任一需求时，再按需演进。

逻辑访问关系（服务间白名单）

虽然 devops-internal 上所有容器理论上互通，但实际业务访问是有向的。下方是推荐的服务间调用白名单，配置应用时按此收敛。

GitLab   → Jenkins   (Webhook 触发 CI)
Jenkins  → GitLab    (拉代码 / 回写状态)
Jenkins  → Nexus     (推制品 / 拉依赖)
GitLab   → RagFlow   (文档同步知识库)
RagFlow  → GitLab    (检索文档源)
Plane    → GitLab    (关联仓库 / MR)
AI Agent → Plane → GitLab → RagFlow → Jenkins  (智能体编排链)
Nexus    → Jenkins/Build Agent  (反向：Agent 拉 Nexus)
